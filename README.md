# FTB Quests 1.16.5 功能回迁补丁

为旧版 FTB Quests 增加 `/ftbquests reload` 和可重复完成的任务字段。独立附加 mod，保留原有 FTB Quests、Teams、Library 和 Money；无需替换它们的 JAR。

**当前版本：1.0.1。可重复任务的默认重置等待时间为 0 秒；是否开启循环，由整合包作者逐项决定。** 安装补丁不会自动把已有一次性任务变成循环任务。

下载编译好的 mod 和分享包：[GitHub Releases](https://github.com/dyfawa4/ftb-quests-repeatable-backport/releases)。只安装 mod 时下载 `.jar`；需要说明和零元任务模板时下载 `-share.zip`。GitHub 自动生成的 Source code 压缩包是源码，不是可安装 mod。

## 适用环境

本补丁按以下实际安装版本编译，并对原始 FTB 字节码验证了注入位置：

| 组件 | 版本 |
| --- | --- |
| Minecraft | 1.16.5 |
| Forge | 本地验证 36.2.42；依赖范围 ≥36.2 且 <37 |
| Java | 11，编译目标 Java 11；本地 JDK 11.0.27 |
| FTB Quests | 1605.3.7-build.165 |
| FTB Teams | 1605.2.3-build.40 |
| FTB Library | 1605.3.5-build.724 |
| FTB Money（仅零元示例需要） | 本地使用 1605.1.4-build.9 |
| Mixin | 本地验证 0.8.4 |

FTB 三个核心组件使用精确版本依赖，避免未经验证的接口差异。其他 Forge 36.2.x 未逐个进行游戏测试。补丁本身不依赖 Pixelmon，也不包含个人路径、用户名、队伍 UUID 或指定整合包名称。

## 安装

1. 完全退出客户端；联机时停止服务端。
2. 将 `ftb-quests-repeatable-1.16.5-1.0.1.jar` 放入该实例的 `mods` 文件夹（源码项目的构建输出位于 `dist`；分享压缩包内位于根目录）。升级时移除旧版补丁，每个实例只保留一份。
3. 多人联机时，服务端和所有客户端都安装同版本补丁，继续保留原有 FTB 模组。
4. 使用 Java 11 重新启动。

首次安装 mod 必须重启。安装后修改任务 SNBT，才可以通过新增的命令重载。旧版原始 FTB Quests 没有这个命令，因此未安装补丁时出现“错误的命令参数”是正常的。

补丁扩展了任务定义的网络数据，使用独立网络通道检查双方兼容性；缺少补丁的一端应被拒绝连接，而不是让不同格式的数据继续读取。

## `/ftbquests reload`

由服务器控制台或权限等级至少为 2 的管理员执行：

```mcfunction
/ftbquests reload
```

读取 FTB 当前实例的 `config/ftbquests/quests`，重新加载任务定义，并向在线玩家同步任务书与队伍数据。命令不重读旧存档中的队伍进度，不清空奖励领取记录，不发放奖励，不修改金币。保留任务、目标和奖励的原有 ID，已有记录才能继续对应原来的对象；更换 ID 属于新建对象。

重载前复制输入文件、检查 SNBT 能否解析，并用独立任务文件对象试加载；当前内存中的任务定义也会保存到 `config/ftbquests/repeatable-reload-backup-*/previous`。发生应用异常时尝试恢复该备份并重新同步，详细错误写入 `latest.log`。备份目录保留供人工恢复，频繁重载会产生多个目录。

命令只添加到现有 `ftbquests` 命令树。原有编辑、进度和其他子命令保留；注册时发现已有 `reload` 会跳过添加。使用 FTB 自身的加载、进度和网络接口；未验证任意第三方任务扩展或另一款同时修改相同方法的补丁。

## 循环任务

### 在游戏编辑器中设置

1. 在游戏聊天栏输入 `/ftbquests editing_mode true`，开启编辑模式。联机由有权限的管理员操作。
2. 右键使用任务书，进入所需章节。
3. 在任务地图上，用鼠标右键单击需要修改的任务节点，选择“编辑”。任务详情页中的绿色加号用于添加目标或奖励；如已打开详情页，先关闭详情再右键地图上的节点。
4. 在任务属性窗口向下滚动，找到下面三个选项。将“可重复完成”设为 `True`，等待时间填 `0`，根据奖励分配方式决定是否等待全队。
5. 点击编辑窗口的保存/确认按钮。通过编辑器修改会提交到服务器，通常无需再执行 `reload`。
6. 输入 `/ftbquests editing_mode false` 关闭编辑模式，按正常玩家流程完成、领取，再检查任务是否恢复。

修改物品兑换任务时，还需要在物品目标里开启“消耗物品”，保证每轮都会扣除提交的材料。作者只需要为希望开放循环的任务开启“可重复完成”，其他任务无需修改。

### 新增字段

| 设置 | SNBT 字段 | 默认 |
| --- | --- | --- |
| 可重复完成 | `can_repeat` | `false` |
| 循环重置等待时间（秒） | `repeat_cooldown` | `0` |
| 等待全队成员领取全部奖励 | `repeat_wait_all_members` | `true` |

例如，独立循环任务中加入：

```snbt
can_repeat: true
repeat_cooldown: 0
repeat_wait_all_members: true
```

流程为：提交目标 → 完成任务 → 领取全部奖励 → 等待冷却 → 恢复目标和奖励领取状态 → 再次提交。默认关闭，因此已有一次性任务继续按原来的规则运行。循环任务不计入章节完成总数。

本实现沿用旧版 FTB 的队伍共享任务进度。默认等待所有当前队伍成员领取奖励，包括离线成员，避免某个人领取后立即清掉其他人的未领取奖励。改成 `false` 时，有任意一名成员领取全部奖励就能重置整个队伍的这项任务。零元刷新任务采用这个设置；有价值的个人奖励建议保留默认值。

重置仅针对该任务，调用 FTB 原生重置接口。检测每 5 个服务端 tick 执行一次，因此冷却结束后还可能等待约 0.25 秒；0 秒表示不额外增加冷却，仍需等待下一次检测，并满足奖励领取条件。低 TPS 时等待会延长。没有目标的纯说明任务不自动循环。

1.0.1 将新任务、缺少该字段的任务和编辑器恢复默认值的等待时间统一设为 0 秒。已明确保存的等待时间继续生效，例如原有任务中的 `repeat_cooldown: 1` 仍是 1 秒，可由作者在编辑器中调整。

这是针对旧版接口实现的核心功能回迁，不保证新版整套任务文件能直接导入。例如新版的完成次数统计、冷却进度 UI 和章节继承设置不在本次范围内。由于完成状态会被重置，循环任务适合独立兑换或刷新节点；不宜直接充当一次性主线任务的永久前置条件。物品兑换任务需要设置消耗物品，才能保证每轮都实际提交物品。

## 点击领取 0 元的示例

`examples/zero-money-refresh.snbt` 是可移植模板。安装脚本生成三个独立 ID，并在所选章节的任务列表末尾追加一项“刷新金币显示（循环测试）”，原有任务保留。模板内 `__..._ID__` 占位符须经脚本替换，不能直接整段复制到游戏。

退出游戏和服务端后，在本项目目录运行：

```powershell
.\install-demo.ps1 -ChapterFile '所选实例\config\ftbquests\quests\chapters\目标章节.snbt'
```

脚本参数由使用者提供，不查找固定游戏目录；原章节备份在本项目 `backups` 下。示例默认位置为 `x=-4,y=6`，可以在编辑器中移动。重复运行不会重复创建示例。

进入世界后打开目标章节，点击勾选目标，0 元奖励自动领取；默认不额外等待，在下一次服务端检测时恢复并可以再次点击。已安装过的示例采用其保存的等待时间，脚本不会覆盖已有设置。联机测试还应检查另一名玩家同步、重新登录、重启后仍能重复，以及原有一次性奖励不能重复领取。

零元奖励的 SNBT 使用当前 Money 模组实际字段：

```snbt
type: "ftbmoney:money"
ftb_money: 0L
random_bonus: 0
auto: "enabled"
```

本地 Money 的奖励编辑器限制最小金额为 1；零元应通过 SNBT 设置，避免编辑金额时被改为 1。当前版本的自动领取字段是 `auto`。

## 与金币显示异常的关系

本地 Money JAR 中，客户端玩家记录未建立时会返回 `9999999` 作为显示值；缺少 `Money` 标签时则可能读到 0。界面显示异常不等于服务器真实余额丢失，具体触发顺序尚未复现确认。

原生金钱奖励调用 `addMoney(player, amount)`。即使金额为 0，也会广播服务器余额，因此这个循环任务提供了重复触发同步的入口；它不会额外增加金币。`/ftbmoney add 玩家 0` 在当前命令实现中会提前返回，不能代替零元奖励。

可以在异常发生时用 `/ftbmoney balance` 对比服务器余额。本补丁增加的是循环和重载能力，不修改 Money 的登录同步代码，不能据此宣称修复了所有金币异常或真实数据损坏。

## 构建和验证

需要 JDK 11、目标实例的 `libraries` 和 `mods`：

```powershell
.\build.ps1 -LibrariesDirectory '实例根目录\libraries' `
  -ModsDirectory '实例目录\mods' -JdkDirectory 'JDK11目录'
```

库中出现多个 Forge 客户端 JAR 时，通过 `-ForgeClientJar` 显式指定。输出包含 JAR 和 `SHA256SUMS.txt`。编译采用 `--release 11`，不下载、打包或重新分发 FTB/Forge/Minecraft 本体。

自动检查覆盖一次性任务、锁定进度、全队/首位领取者、离线未领取者、冷却边界和溢出、三轮独立提交的状态模型；另用 Mixin 0.8.4 在客户端及服务端环境对实际 FTB 类应用全部七处注入，并验证生成的字节码。状态模型不等于实际游戏中的奖励发放测试。

游戏内操作、多玩家同步与重载后的第三方任务行为由使用者测试；当前构建尚未据此宣称全部通过。

已有用户在当前整合包中确认循环任务能够正常恢复。1.0.1 修改默认等待值，并通过了同一组离线检查；多人联机、金币异常触发和各种任务类型尚未进行完整实机覆盖。`reload` 的实际游戏表现也需要单独验证。

### 建议作者验证的项目

- 勾选目标的循环任务连续完成三次，每次需要重新提交，领取奖励后恢复。
- 普通一次性任务领取后不能再次领取。
- 消耗物品的兑换任务每轮只扣除一次材料、发放一次奖励。
- 两名玩家组队：开启等待全队时，第一人领取后仍保留第二人的奖励；两人领完后才恢复。离线成员的未领取状态同样会等待。
- 零元刷新任务领取后真实余额不变；用 `/ftbmoney balance` 对比服务器数值。
- 外部修改任务定义后执行 `reload`，已完成任务和已领取奖励保留；退出重进及重启后检查设置和记录。

## 常见问题

**0 秒为什么不是点击后同一瞬间恢复？** 服务端每 5 个 tick 检查一次，0 秒仅取消额外冷却；正常 TPS 下还可能等待约 0.25 秒。所有目标完成、奖励领取条件满足后才恢复。

**设为 0 但一直不恢复？** 检查是否还有未领取奖励，以及“等待全队”是否开启。默认开启时，离线队友也需要领取；零元显示刷新任务通常选择关闭等待全队。

**为什么新默认为 0，但旧任务还显示 1？** 已保存的显式设置优先。手动编辑该任务即可，升级不会替作者批量改动已有任务。

**为什么没有新增选项或 reload 命令？** 确认启动的是正确实例、补丁被 Forge 加载且已完整重启。联机需要服务端也安装；编辑选项需要开启编辑模式。原始版本没有这个重载命令。

**报重复 mod 或依赖不满足？** 每个实例只保留一个版本的本补丁，保留原有 FTB 模组，按上面的版本表检查依赖。不要同时安装旧、新两个补丁 JAR。

## 卸载与授权

关闭客户端和服务端后移除本补丁 JAR。旧 FTB 会忽略新增字段，循环任务恢复为普通一次性任务，补丁添加的 `reload` 命令也随之消失。测试任务需要手动删除或恢复章节备份；不要用历史章节备份覆盖后来新增的任务而不检查差异。
